# ADR 0010: Runtime-tunable configuration without redeployment

- **Status:** Accepted (Ali, in chat, 2026-11-11); previously Proposed (2026-11-11), for Ali's acceptance. **Partially supersedes ADR 0009** (§1 "Loading": the last sentence; §3 the env-var rollback; §4 for flags that are safe to flip live; two rows of "Not doing now"). 0009's text is not rewritten; it carries a pointer to this ADR.
- **Evidence:** ADR 0001, 0002, 0006, 0007, 0009; `docs/research/2026-11-11-judges-and-wow-moment.md` (cuts approved; the compliance-report LLM drafter is kept as one bounded, read-only feature). Sources checked 2026-11-11 are cited inline.

## Context
Ali's requirement: every hyperparameter and tunable parameter can change without a redeployment. Under 0009, an env change creates a new Container Apps revision (a restart, no rebuild), and rules are loaded once and never hot-reload. 0009 rejected hot-reload for two reasons: unreviewed changes, and the loss of the revision as the audit trail. A design that meets the new requirement has to answer both.

**Challenge to the requirement.** Taken literally ("all"), the requirement would make legal floors editable at runtime. ADR 0006 and the plan forbid that. It would also make physics and prompts editable, and those are only valid with tests or evals. The requirement is right for one class of values: operating values we expect to tune after the back-test, where a restart adds risk for no gain. Examples are the TWL margin (ADR 0006), the probability bands and the planner weights. A switch between models that are already present also belongs here. So the requirement holds per class, below, and does not hold for classes (c) and (d). The cost is about 1.25 build-days (B1 +4 h, B3 +3 h, F2 +3 h). The approved cuts free 6-9 days, so they fund it.

## Decision

### 1. Parameter classes
| Class | Examples | Where it lives | How it changes | Live? |
|---|---|---|---|---|
| **(a) Training hyperparameters** | LightGBM params, quantile grid, CQR strata and hour-band edges, calibration windows, feature set | `backend/training/configs/<name>.toml`, validated by a frozen `extra="forbid"` `TrainingConfig` | Edit in a PR, then train. A training run is **not a deployment**: it produces an artefact. | n/a (offline) |
| **(b) Runtime tunables and flags** | TWL margin; probability bands; alert lead times; de-escalation dwell; planner soft-cost weights; calibration pair; k-suppression (above its floor); active model id; ruleset pin; LLM route selection (§8); flags safe to flip live (for example the compliance-drafter kill switch) | Postgres `config_version` rows (immutable), with the active one given by an append-only `config_activation` log. The seed comes from git (`backend/config/runtime/default.toml`) | Admin API or CLI, validated, audited, with no restart | **Yes** |
| **(c) Legal and regulatory floors** | ADOSH TWL zone edges 140/115; midday-ban window and dates; work-hour and break limits; NIOSH acclimatization schedule and Table 3-2 clothing adjustments; withdrawal-limit decision; k-suppression floor; "PERSONAL data never leaves our infrastructure" for LLM calls (§8) | Ruleset TOML (ADR 0009: lock hash, golden tests), loaded only from the image | New ruleset file, then PR, CI and an image release | **No, by design** |
| **(d) Needs a code change** | REL/RAL, Liljegren, TWL solver and PHS coefficients; boundary conventions; the set of tunables and their types; the alert-level enum; the "escalate immediately" invariant; RBAC, consent and purpose rules; API shape; LLM drafter prompts (need an eval run) and its `temperature = 0` (determinism) | Code | PR and release | No |
| (wiring, not a tunable) | DB URL, secrets, `SB_ENV`, log format, `SB_FORECAST_SOURCE` per container, `SB_ENABLE_WHATSAPP_ADAPTER` (rejected in prod, ADR 0004), LLM endpoint and key | Env (12-factor, ADR 0001) | Infra change (a new revision) | No |

**(a) Versioning and linkage.** `sb-jobs train --config <path>` (B2) is the only entry point. It refuses command-line hyperparameter overrides. With `--release` it also refuses a dirty git tree. The model id becomes `corrector-<yyyymmdd>-<gitsha7>-<cfg6>`, where `cfg6` is the first 6 hex characters of the training config's SHA-256. Two configs trained at one commit therefore cannot collide. `manifest.json` gains `training_config_path`, `training_config_sha256` and the resolved config (ADR 0007's `params.json` stays). The decision row's `model_id` therefore leads back to the exact hyperparameters.

**(b) Calibration level is live only among the pairs that were calibrated.** CQR offsets exist per symmetric pair (ADR 0007). `calibration_pair` (for example `0.10/0.90`) is validated against the active model's manifest. Any other coverage level is a class (a) change, because it needs recalibration.

**(b) Stability limits only delay de-escalation.** `deescalation_dwell_minutes` holds a level before it drops. Escalation is always immediate. This is a code invariant (class d) with a hypothesis property test. No tunable can hold back a warning.

### 2. Mechanism: versioned config in the existing Postgres (chosen) vs Azure App Configuration
| | Postgres (chosen) | Azure App Configuration (checked 2026-11-11) |
|---|---|---|
| Cost | $0 extra | Free: 1,000 requests/day, then HTTP 429 "until midnight UTC", and frequent sentinel reads are not excluded on Free. A single client refreshing every 30 s makes 2,880 requests/day. Developer: $0.12/day, 3,000 requests/day included, no SLA. Standard: $1.20/day (about $36/month, half the $75 budget). Prices from the Azure Retail Prices API for `uaenorth`; quotas and SLA from the MS Learn App Configuration FAQ |
| UAE North | Already deployed | Available (UAE North meters in the Retail Prices API; UAE North is listed in the FAQ's availability-zone table) |
| SDK | none new | `azure-appconfiguration-provider` 2.5.1 (PyPI, 2026-10-30), Microsoft-maintained, with an async variant. It also pulls in `azure-identity`, and bootstrap needs a Data Reader role assignment |
| Refresh | Background poll every `config_poll_interval_s` (default 5 s), plus an immediate local apply on the replica that activates | Pull only and activity-driven: "call the `refresh` method", "a no-op before the configured refresh interval elapses" (default 30 s), a sentinel key via `refresh_on`, and the provider keeps the cached config when a refresh fails (MS Learn, Python provider reference) |
| Validation before activation | The same Pydantic models, plus bounds and floor checks, run server-side **before** the pointer moves, in one transaction with the audit row | The store accepts any value. Validation can only happen in the client after the change, so "active in the store" can differ from "applied by the app" |
| Audit and decision linkage | `config_version_id` and `config_sha256` are a foreign key on every decision row. Audit events go to the governance trail. History is permanent | Revision history is kept 7 days (Free and Developer) or 30 days (Standard). Actor and reason sit in a second system |
| Dependencies on the safety path | None new | A second stateful service (the reason ADR 0002 and 0009 gave) |

The provider is healthy and the region is supported, so neither of those decides it. Two things do. First, App Configuration cannot validate a value before it goes live, and it cannot share a transaction with our audit trail. Second, it is one more dependency, which goes against ADR 0002's minimalism. Its refresh is also a pull, so it would not propagate changes any faster.

**Postgres LISTEN/NOTIFY is deferred.** A notification reaches only the sessions that are listening when it is sent. A listener whose connection dropped misses it, so a poll is needed as the backstop anyway. With one replica, the 5 s poll alone meets "no restart". The trigger to add LISTEN/NOTIFY is below.

### 3. Data model and flow
- `config_version`: `id bigint identity`, `sha256 char(64) UNIQUE` (canonical JSON: sorted keys, compact), `body jsonb`, `schema_version int`, `created_by text`, `reason text` (both `NOT NULL`, CHECK non-blank), `created_at`. A trigger rejects UPDATE and DELETE.
- `config_activation`: `id`, `config_version_id` (FK), `kind` (`seed` | `activate` | `rollback`), `actor`, `reason`, `activated_at`, and `previous_activation_id` with **`UNIQUE NULLS NOT DISTINCT`** (Postgres 15+). This is optimistic concurrency with no lock: two activations racing on the same predecessor produce one unique violation, which surfaces as `409 stale-activation`, and only one seed can ever exist. The table is append-only (trigger). The active version is the latest row.
- `RuntimeConfig` (pure domain, frozen, `extra="forbid"`) holds `ruleset_pin`, `model_id`, `tunables` and `flags`. Floors are absent from it, so a payload that tries to set one fails schema validation.
- **Activation path:** parse with Pydantic; check bounds; check floors; check the model id against the in-image registry and the calibration pair against that model's manifest; preload and smoke-predict the model. Then a single transaction inserts the activation row and the audit event. Then the activating replica swaps its in-memory snapshot. **Every replica re-runs the same validation when it loads a version** (defence in depth: a row inserted by hand through SQL is refused). If a replica refuses a version, it keeps the last good snapshot, logs `config_rejected`, writes the audit event, and reports `checks.config = "stale"`.
- **Snapshot semantics:** the active snapshot (`ConfigSnapshot`: version id, sha, `RuntimeConfig`, resolved ruleset, loaded model) is swapped atomically as a reference. A request or job run reads one snapshot and keeps it until it finishes, so versions never mix inside one decision. `job-refresh` reads the active version once at the start of each run.
- **Rollback:** `POST /api/v1/admin/config/rollback` (or `sb-jobs config rollback`) activates the version of the previous activation, with `kind = rollback`. It goes through the same validation and needs no new revision.
- **Startup:** the app needs the DB-active version. If the DB is down or nothing is seeded, readiness is 503 (`dependency = "config"`) and decision routes return 503 problems. The app never serves on an unknown config (0009's loud-failure stance). `sb-jobs config seed` runs in `job-migrate` after `alembic upgrade head`. It is idempotent: it inserts the git default if its sha is absent, and activates it only when no activation exists.
- **Every decision records its config.** Decision and alert rows gain `config_version_id bigint NOT NULL` (FK) and `config_sha256 char(64) NOT NULL`, next to 0009's `ruleset_id`, `ruleset_sha256` and `model_id`. Decision-carrying responses and `RiskPolicy` add `config_version` (additive; `policy_version` stays the ruleset id). `job_run.params` records the version for the run.

### 4. Guardrails
1. **Floors are not in the runtime schema** (structural, class c).
2. **Each tunable has a reviewed range.** The ruleset declares a `[tunables.<name>]` table with `default`, `min`, `max`, `safer = "higher" | "lower" | "none"` and `source`. A runtime value outside `[min, max]` is rejected. The less-protective end of the range is set in the PR and pinned by the golden tests. Example: `k_suppression` has min 5, the privacy floor. A tunable that is not declared in the active ruleset is rejected.
3. **Ruleset pins cannot relax the law.** Every floor field carries a comparator (`Floor(safer=...)`; a floor without a comparator fails schema load). In prod, a pin is accepted only if it is released, covers today (Asia/Dubai), and every floor is at least as protective as the floor in today's date-resolved ruleset. This gives instant rollback to a previous ruleset when the floors did not change, and refuses it when the law tightened. A pin never applies outside its effective range: the catalog raises.
4. **Actor and reason.** Writes need `Authorization: Bearer`. `SB_ADMIN_TOKENS` (a Container Apps secret) maps actor to the SHA-256 of a token, compared with `hmac.compare_digest`. The actor comes from the token, never from the body. `reason` is required, 10-500 characters. CLI writes need DB credentials, `--actor` and `--reason`. Auth failures are audited.
5. **Governance audit trail.** `config.version_created`, `config.activated`, `config.rollback`, `config.rejected` and `config.auth_failed` go to B3's append-only audit table, in the same transaction as the activation. Until B3, the activation row itself carries the actor and the reason, so nothing is lost.
6. **Env pins are not used in prod.** With `SB_ENV=prod`, a set `SB_RULESET_ID` or `SB_MODEL_ID` fails startup with "use the runtime config (ADR 0010)". That keeps one source of truth. In dev and test, the pins build a file snapshot for back-tests and DB-less runs.

### 5. Model hot-swap
Artefacts stay **baked into the image** (ADR 0002: no object store). `ModelRegistry` scans `backend/models/*/manifest.json` at startup and verifies every hash. The image keeps every released model id, not just the current and previous ones. Activating a `model_id` loads the model lazily, warms it on a pinned fixture, then swaps it in. The old model is freed once in-flight requests finish. Switching between models that are present needs no redeploy. Making a **newly trained** model available is a release, because it needs an image build. Fetching models from blob storage is parked, with a trigger.

### 6. Scaling to N replicas
Each replica polls; config state is already in Postgres, so no Redis is needed (this answers the "more than one replica" trigger in ADR 0002 for this state). Replicas converge within about the poll interval plus the model-load time. During that window they may serve different versions, and each decision says which one it used. Postgres load is one indexed single-row read per replica every 5 s. I1 Task 9's cost check confirms that the poll keeps the `api` replica at the idle rate (under 1,000 B/s, ADR 0001).

### 7. Reconciliation with ADR 0009
**Stays file-based (0009 unchanged):** ruleset TOMLs as the git source of truth for floors, defaults and tunable ranges; `lock.json`; golden tests; drafts refused in prod; date resolution; the model manifest and its hashes; `composition.py` and its registries; the import contracts. **Moves to DB-active:** which version is active (ruleset pin, model id, tunable values, live flags). **Superseded:** 0009 §1 "Rules never hot-reload" (rules still never hot-reload; *operating values* now do, within reviewed ranges); §3 rollback via `SB_MODEL_ID` and a new revision (now a runtime activation); §4 for live-safe flags (they move into `RuntimeConfig.flags`, still each added with the code it gates); the "Not doing now" rows "Flag SaaS / ... Azure App Configuration" (re-decided in §2 above, same outcome, new reason) and "Hot-reload or DB-edited rules (admin UI)" (operating values only; rules stay files).

### 8. LLM routing by data class
The `LlmClient` port stays deferred (ADR 0002). The only exception is the kept compliance-report drafter, a bounded, read-only feature over aggregated, k-suppressed data. The rule below is fixed now so that any future LLM feature follows it.
- **The data class is declared, never inferred.** Every call takes `LlmInput[D]`, a frozen typed wrapper, where `D` is `NonPersonal` (aggregated or de-identified) or `Personal`. The class is set by the code that builds the input, and it has no default. The drafter's builder accepts only k-suppressed aggregates, so its output type is `LlmInput[NonPersonal]`. Nothing classifies the text after the fact.
- **Routes.** The route catalog is wiring (env, an infrastructure change). Each route has an `id`, an OpenAI-compatible `base_url`, a `model` and `hosting: managed | self_hosted`. The catalog is never editable at runtime, so a route cannot be relabelled. `RuntimeConfig.llm_routes = {non_personal: <route id | null>, personal: <route id | null>}` is runtime-tunable (class b): you can switch routes or turn them off live.
- **Floor (class c, non-relaxable): PERSONAL never leaves our infrastructure.** A `personal` route must be `self_hosted`, meaning an OpenAI-compatible server we run (vLLM, llama.cpp server or Ollama, behind the one `openai`-client adapter ADR 0002/0008 already describes). In production it runs inside the UAE. In development, the local RTX 3080 16 GB can serve a quantized model of about 14B. `NON_PERSONAL` may use a managed API. The rule is enforced in three places:
  1. `validate_runtime_config` rejects a `personal` route that points at a `managed` route (`floor-violation`).
  2. The managed adapter's signature accepts only `LlmInput[NonPersonal]`, checked by mypy, plus a runtime `isinstance` check.
  3. The router **fails closed**: if no `personal` route is configured, the call is refused with a problem and an audit row. It never falls back to the managed route.
- **Second line of defence:** a pre-call PII detector runs on every `NonPersonal` payload. A hit refuses the call and writes `llm.pii_blocked` to the audit trail. It does not silently reroute, because a hit means the builder has a bug. The detector library is chosen and pinned when the port is built.
- **Proof:** a unit test shows that a `Personal` payload cannot reach the managed adapter. It covers the type-level rejection (a `reveal_type`/mypy check in CI), the runtime check, the fail-closed refusal and the config floor. No PERSONAL-data LLM feature is in demo scope.

## Not doing now
| Option | Why not | Trigger |
|---|---|---|
| Azure App Configuration / OpenFeature / flag SaaS | §2 | Several services or tenants share config; percentage rollouts or targeting needed |
| LISTEN/NOTIFY wake-up | The poll suffices; NOTIFY is lost while a listener is disconnected | Propagation under 1 s needed, or more than 3 replicas |
| Rulesets stored or edited in the DB | They would bypass the lock, the golden tests and review | A non-engineer must change law-derived values without a release |
| Blob-fetched models (`ObjectStore` port) | Baked-in models suffice | A new model must go live without an image build, or the image grows past about 200 MB of models |
| Four-eyes approval of activations; Entra ID admin auth | One admin in the demo | Before any pilot |
| Separate DB roles (the app cannot drop its own immutability triggers) | The demo connects as `sbadmin` (I1) | Stage 2, with Entra DB auth |

## Consequences
- Tuning the margin, bands, weights or lead times after the 15-16 Nov back-test is an audited API call, not a deploy, and the demo can show it: change, audit row, new `config_version` on the decision.
- One new migration (`0002_runtime_config`), one port with a Postgres adapter and a fake, one poller, and the CLI commands. No new dependency and no new Azure resource.
- A deploy whose new ruleset makes the active pin invalid fails readiness. The old revision keeps serving (ADR 0001), and the admin activates a compatible version. The failure is loud, by intent.
- The worker device computes personal risk from `RiskPolicy`, so it must use the policy whose `config_version` matches the forecast's. When offline, it shows the cached versions (F2).
- Demo-time limitation: a static bearer-token map, not real identity. State it in the technical document.
