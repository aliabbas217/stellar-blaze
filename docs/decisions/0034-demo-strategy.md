# ADR 0034: Demo strategy: replay-mode wow (Warnings + Plans scoreboard), real-work layer, climate what-if as SHOULD, fixed cut order

- **Status:** Accepted
- **Date:** 2026-11-11
- **Deciders:** Ali; the architect (Claude)
- **Supersedes / superseded by:** none. Adopts `docs/research/2026-11-11-judges-and-wow-moment.md` v2 §0, §4, §8-§10 (v2 §10 supersedes v2 §3 where they differ) and answers its §10.1 decisions
- **Evidence:** Judges v2 §0 (bottom line), §2.1 (assumed strong field), §4.4-§4.6, §8, §9.1-§9.2, §10, §10.1; ADR 0011 v2 §9, §11; roadmap "Decisions recorded 2026-11-11" (Demo line)

## Context
The top three is chosen across all ten statements, so the bar is the best entry anywhere (Judges §0.1). We design against an assumed strong field whose table stakes are a live WBGT dashboard, simulated wearables, an LLM copilot, a risk map, multilingual alerts and a film (§2.1). What only our data can show: warnings scored against thermometers on a held-out summer, with the forecast as it stood the evening before. Live weather during judging (20-30 Nov) and GITEX (7-11 Dec) will be mild.

## Options considered
| Option | Evidence | Verdict |
|---|---|---|
| Live-weather dashboard as the centrepiece | Table stakes; mild weather at judging | Rejected |
| Optimiser headline ("we move the shift and save X%") | Does not survive law + sleep (ADR 0033) | Rejected |
| "Summer 2026, replayed honestly" scoreboard + real-work + potential layers (chosen) | Judges §4, §8, §9; ~3.1 days with the climate toggle, ~2.4 without | Accepted |

## Decision
1. **Replay mode is the demo spine** (`ReplayForecastSource`, ADR 0002). Order: wow (50 s) → real work (20 s) → potential (25 s).
2. **Wow: the scoreboard, two rows.** Warnings: ban-only vs naive WBGT ≥ 32 vs ADOSH zones on raw IFS vs Stellar Blaze, on held-out 2026 at OMAA (pre-registered site), then one pre-registered day, then the worker card. **Plans**: naive schedule vs ban-only vs rule plan on raw vs rule plan on the corrected protective quantile, scored by the independent validator against truth zones (ADR 0011 §9 metrics 1-3), each with a 95% interval. Never say "minutes avoided" or "illness prevented".
3. **Pre-registration** of metrics, demo day, Plans metrics and the climate method is committed on 12 Nov, before 2026 is scored.
4. **Real-work layer:** pre-registered protocol + reliability diagram; the validator's clause-cited violation list with a judge "try a plan" input; the roster frontier chart (ADR 0024); "proof" chips on every number, generated from exporter `provenance` blocks.
5. **Climate what-if is SHOULD** (17 Nov, only if the 16 Nov gate is green): 2026 replayed at +1.5 / +2.0 °C global warming level from the **IPCC AR6 Atlas, Arabian Peninsula region including sea (ARP landsea, headline)**, land reported too; humidity shown as a **range** (specific humidity fixed vs RH fixed); labelled "sensitivity scenario on a real summer, not a forecast"; no calendar year in the headline. If cut: a static slide or a roadmap line.
6. **The legalisation gain (7.5% / 19.1%) is credited to the law**, shown only on the frontier chart, never on our scoreboard (Judges §10.1 decision 3).
7. **A roadmap screen** ("What's next", status chips exists / designed / needs pilot).
8. **Cut order if late:** climate what-if → validator "try a plan" input → proof chips → Plans row (kept in the report and deck).
9. **Never cut:** the Warnings scoreboard (fallback: a static chart of the same JSON), the pre-registration, the governance refusal (employer → 403 → audit row visible to the worker). Roadmap §7's never-cut list also holds.

## Consequences
- If the numbers disappoint, the Judges §4.5 table applies, decided now: the scoreboard ships with the honest result.
- **Cost of being wrong:** about 2.4-3.1 marginal days go to evidence instead of features; if judges reward visible breadth over verified depth, we score lower on "working solution". Mitigated by the scoreboard being a working screen, not a slide.

## Revisit trigger
The B1 Task 11 data gate fails on 12 Nov (the scoreboard has no data); the A6 schedule re-check on 13 Nov shows the marginal days do not fit; or organisers publish judging weights or named judges that change the criteria balance.

- **2026-11-15 (B3 ruling R-AG: the replay clock; decision text unchanged).** In replay mode the domain clock (stop start and clear times, `signed_at`, the `now` of use cases) is a `ReplayClock`: it starts at `SB_REPLAY_NOW`, or at `SB_REPLAY_DEFAULT_DATE` at 11:10 Asia/Dubai when that is unset, and then runs at real speed (a restart returns it to the anchor; stops and sign-offs persist as rows of the replay day; demo reset, ADR 0066, is the way out). The wall clock still drives the rate limiter, the reset timestamp and the audit `at`. Two consequences for the demo script. (1) 11:10 is crew B's midday break (shifts 06-11 and 15-18), so a stop at the default anchor stops the **afternoon** block, not live work: set `SB_REPLAY_NOW` to a time inside the morning block (about 10:10 local) for the live-stop moment. (2) `SB_REPLAY_NOW` and `SB_REPLAY_DEFAULT_DATE` that name different days are not validated; the demo checklist checks both. **Cost of being wrong:** a stop demonstrated at 11:10 shows no effect on current work. **Revisit trigger:** a live mode on the same URL.
- **2026-11-15 (replay clock anchored in Postgres; decision text unchanged; refines the replay-clock entry above).** The I1 rehearsal found that the demo window is about 7 h 20 min after the api process starts (the replay time passes 17:30 Dubai), and that the api and the `alerts` worker each keep their own clock in memory, so an api restart in the cloud silently desynchronises them. **Ruling:** in replay mode the domain clock is `replay anchor + (wall time now - start of the current epoch)`, where the epoch start is read from the `site_epoch` row in Postgres, so the api, the alerts worker and any restart agree. A demo reset (ADR 0066) starts a new epoch and therefore re-anchors the clock to `SB_REPLAY_NOW` (default 11:10 on `SB_REPLAY_DEFAULT_DATE`). The deploy runs one reset at the end, and the runbook says to reset before each judged session. **Cost of being wrong:** one extra read of the epoch row per clock read (cacheable for a few seconds); a window of about 7 h 20 min per epoch still applies, after which a reset is needed. **Revisit trigger:** a live mode on the same URL.
- **2026-11-17 (the clock, web side; decision text unchanged; refines the two replay-clock entries above).** The first live deploy (France Central, image `2b56199c73e1`) showed the supervisor screen reading "off shift" for all four crews. Cause, verified in the repo: the web app applied a hard-coded `REPLAY_HHMM = "11:10"` to the forecast's date, while the API clock starts at `SB_REPLAY_NOW` (10:10) and runs at real speed; 11:10 is inside the crews' midday break. **Ruling:** in replay mode the web app has no clock of its own. `GET /sites/{id}/forecast/today` carries an additive optional member `now`, the API's domain clock (replay anchor plus real time since the epoch started; wall time in live mode). The web keeps it together with the monotonic time at which the response arrived, shows the reading plus the time elapsed since, and re-syncs on every forecast response, so the header, the crews screen and the Stop stamps agree. `?at=HH:MM` stays the judge's time travel. With no reading the web shows `--:--` and never an invented time. `SB_REPLAY_NOW` stays 10:10, and the web's constant 11:10 is removed; a unit test fails if a clock-time literal returns to the demo clock code. **Consequence:** a web build needs an API that sends `now` (without it the supervisor screens stay on "Loading" in replay mode), so deploy them together; the deploy script does. **Evidence (live, image `4f517750a95c`, epoch 4, 2026-11-17):** epoch 4 started at 06:24:22Z; at 06:27:03Z the API's `now` was 06:12:41Z, which is 10:12:41 Dubai, exactly 10:10 plus 2 min 41 s; about 40 s later the supervisor page showed "Time at the site 10:13", "Now 10:13" and all four crews on shift (Orange until 11:00). Not measured: a cold offline start, where the service worker may serve a cached forecast and the clock would be the cache time plus elapsed time.

- **2026-11-20 (window repeats; decision text unchanged; amends the replay-clock entry of 2026-11-15 above, whose formula `anchor + (wall now - epoch start)` runs on without end).** Seen live on 2026-11-20: about 50 hours after the last demo reset the supervisor screen read "Highest level, off shift now, No level for Crew A" at 13:34, because the clock had run past 17:30 and across days, and the crews' shifts end by 18:00. Judging runs 20 to 30 November and nobody resets the demo in between, so "reset before each session" cannot be the way to stay inside the day. **Ruling:** in replay mode the domain clock is `anchor + ((wall now - epoch start) mod 7 h 20 min)`, still read from the `site_epoch` row and still at real speed inside the window. The window is half-open, `[anchor, anchor + 7 h 20 min)`: at the deployed anchor (10:10 Dubai) the last reading is 17:29:59 and the next second reads 10:10:00, so a judge who opens the demo at any hour of any day sees a working day. A reading before the epoch start is still the anchor. The function is pure (`replay_reading`), so the api and the `alerts` worker, which share the epoch row, give the same domain time for the same wall second through every wrap; within one cycle the reading is still monotone, and a wall clock that steps back over the wrap holds the reading it gave. **Kept as it was:** a demo reset starts a new epoch and re-anchors to the anchor; live mode (not replay) is the wall clock; `SB_REPLAY_NOW` set explicitly is the anchor and the window is `SB_REPLAY_NOW + 7 h 20 min` wherever that is (an anchor at 18:00 gives 18:00 to 01:20; the window is not fixed to 17:30); Asia/Dubai has no DST, and the code compares only timezone-aware instants (naive ones are refused). **Consequences.** (1) Rows of the replay day are scoped by epoch and carry domain timestamps, and nothing is deleted. A stop or sign-off made in one cycle belongs to the same epoch in the next, so it comes back at the same domain time: a stop recorded at 16:10 is in the domain future in the next cycle and covers 16:10 to the end of the crew's shift again when the clock reaches it; resuming it earlier in a later cycle ends it at its own start (`greatest(now, started_at)`), which is an undo and covers nothing. Nothing crashes (tests in `test_replay_clock_routes.py`). The audit `at` is the real time and is unaffected, but `started_at`, `cleared_at` and `signed_at` of one epoch are no longer increasing across a wrap. A reset clears all of it from the demo. (2) The 60 s site-day cache treated a negative age as fresh, so a day cached at 17:29 would have been served for the whole next cycle; a negative age is now a miss (this also applies after a reset and in live mode when the wall steps back). (3) The web is unchanged: it shows the API's `now` plus the monotonic time since the response. It cannot know the window end, so a page that stays in the foreground across the wrap with no forecast refetch keeps counting past 17:30 until its next forecast response (a refocus or navigation once the response is 30 to 60 s old, the query staleTime) re-syncs it to the API's reading; parked. (4) The run recipes and the infra scripts still say a reset is needed after about 7 h 20 min, and `smoke-http.sh` H4 and the deploy warning check for it: that is now conservative, not wrong, and is parked, not edited. **Cost of being wrong:** a demo with two judged sessions in one epoch can show the first session's stop or sign-off again at its domain time in the second (a reset between them removes it); domain time jumps back 7 h 20 min once per window; and the day is always the same working day, so a judge who waits sees it repeat. **Revisit trigger:** a live mode on the same URL; a judge reporting a stop or sign-off they did not make; the API carrying the window end so the web can re-sync at the wrap.
