## 2. Design calls (for the architect)

1. **Replay clock: epoch based since B3 b731bd4 (ADR 0034 amendment, 2026-11-15); the I1 scripts were first written for the earlier process-start clock and were changed.** In replay mode the domain clock is `SB_REPLAY_NOW anchor + (wall now - start of the current epoch)`, the epoch start read from the `site_epoch` row in Postgres, so the api and the alerts worker agree and a restart of either does not desynchronise them. `sb-jobs site load` writes epoch 1 when it first creates the site, so the window (about 7 h 20 min, replay time passes 17:30 Asia/Dubai) starts at the FIRST deploy; later deploys do not start a new one. What the deploy therefore does: it ends restart, a demo reset (`POST /api/v1/sites/site-demo-mussafah/demo-reset` through the web BFF, which injects the token; `infra/scripts/reset-demo.sh`, `deploy-local.ps1 -Action ResetDemo`), the smoke test and a final reset, and the runbook says to reset before every judged session. A reset starts a new epoch, so stops, sign-offs, alert events and push subscriptions of the old epoch are not read any more: subscribe a phone AFTER the last reset. The reset is limited upstream to 1 per 60 s and 10 per hour, and the BFF general bucket counts it too (smoke H6 drains that bucket for about a minute), so the smoke test is followed by a pause before the final reset. Smoke H4 reads the api's replay "now" from the `started_at` of its own test stop and fails when it is outside 10:00-17:30 Asia/Dubai. `restart-apps.sh` (api, alerts and web back to back) remains for a different reason: Container Apps creates no revision when only secret VALUES change, so rotated secrets reach running replicas only after a restart. The rehearsal (`infra/local/rehearse.sh`) must run unchanged on the merged tree.
2. **The api is NOT public** (architect ruling 2026-11-15; changes the plan's "both: external ingress"). On Azure the `api` app has internal ingress (`external: false`) and `web` calls it at `https://<api internal FQDN>` (port 443, no port in the URL); on Render the api is a private service. Reason: the web BFF holds the demo token and the per-client and global rate limits (ADR 0062); a public api would let a caller skip both. Consequences: the deploy gate and the smoke test never call the api over HTTP; they gate on the revision's own state (`az containerapp revision show`: `latestReady == latest`, image, `Provisioned`, `Running`, `Healthy`, replicas) and on the web BFF routes (`/api/v1/health/ready` through `web`, the stop and its undo). Container Apps is documented to answer 404 to a call from outside the environment (Microsoft Learn connect-apps; not verified here). **Unverified:** that Node trusts the certificate on the `.internal.` FQDN (Microsoft's docs do not say who signs it), and that Bicep exposes `ingress.fqdn`. The fallback, kept OFF and written as a comment in `main.bicep`, is `API_ORIGIN=http://<app name>` with `allowInsecure: true` on the api ingress (reachable only inside the environment). The web BFF health check through `/api/v1/health/ready` fails at once if the certificate is the problem.
2a. **`--forwarded-allow-ips "*"` in the api image CMD** (`backend/Dockerfile`; not changed). With the api private, its only peer is `web`, and the BFF forwards only `content-type`, `accept` and `x-request-id`, never `X-Forwarded-For`; the api uses the client address for log lines only (its limits are per token, ADR 0062). So `*` is acceptable here only because the api is private; the stated reason is in the runbook.
2b. **`TRUSTED_PROXY_HOPS`**: 1 on Azure, documented (Container Apps provides only the rightmost `X-Forwarded-For` entry and appends to a client value; Microsoft Learn ingress-overview). On Render the number of proxies is NOT documented (Cloudflare is in front; the docs do not describe the header), so it is 1 (too few hops fails safe, too many fails open) and the smoke check H6 (30 requests with forged `X-Forwarded-For` values must still hit a 429) is the proof on the public URL. The compose rehearsal puts an nginx in front of `web` that appends like the Container Apps ingress, and also shows that without the proxy the forged header does evade the per-client bucket.
3. **Burstable B1ms** is documented by Microsoft as "not recommended for production workloads" and without 24/7 support; acceptable for a demo, stated in the runbook.
4. **The migration is not skipped silently** (delta 9). A real deploy with no `job-migrate` fails.
5. **`ssl_min_protocol_version`** on Postgres is left at the default (the Microsoft best practice is TLSv1.3; not set so as not to add an untested failure mode).
6. **Local deploy path is native PowerShell** (`infra/scripts/deploy-local.ps1`), not the bash scripts: Git Bash rewrites `/subscriptions/...` arguments and `az.cmd` output carries `\r`, both of which only show on Windows against a real `az`, which cannot be tested here. The two paths share one contract (same Bicep, same checks); the HTTP smoke test exists twice (`smoke-http.sh`, `Test-DemoHttp.ps1`) and both were run against the local compose stack.
7. **Secrets for the local path** live in `%LOCALAPPDATA%\stellar-blaze-i1\secrets.json` (outside the repository, never printed) and are generated by `deploy-local.ps1 -Action InitSecrets`, including the VAPID key pair (P-256, generated in PowerShell and checked against the backend's `py_vapid`).
8. **Render fallback keeps ADR 0042 (architect ruling 2026-11-15: no exception).** Render's managed Postgres documents that internal connections "do not support sslmode=verify-ca or sslmode=verify-full" (self-signed certificates), so it is NOT used. The fallback runs Postgres as a Render private service (the official `postgres` image, a persistent disk, a server certificate from a CA we generate with `infra/scripts/gen-db-certs.sh`, supplied through environment variables) and gives `api`, `alerts` and the migrate step the CA root through `PGSSLROOTCERT`. The certificate's subject alternative name must equal the private host name that Render assigns, which is only known after the service exists, so the first apply is followed by a second pass (runbook). If a verifying connection cannot be had, the Render files stay out of the deploy path (marked "not verified for TLS") and the last-resort fallback is the local stack plus the video. `ssl=require` is never shipped.
8a. **Local stack (plan Task 8) is a MUST and a production rehearsal** (architect ruling). LocalStack was researched and rejected: Azure support is a public preview behind a token, `what-if` and `validate` are not implemented, federated credentials and budgets are missing, no Container Apps cron triggers, registry pull by managed identity unstated, and its Postgres demo uses `sslmode=require`; those are exactly the risky parts of the Bicep. `infra/local/rehearse.sh` runs db with TLS from a run-time CA and a TLS-only HBA, `migrate` then `site load`, api, the alerts worker, web, and an nginx that appends `X-Forwarded-For` like the Container Apps ingress; then the smoke test through the proxy and negative checks (plaintext refused, wrong CA, wrong host name, missing root, `ssl=require` connects, forged header evades the limiter only without the proxy).
9. **First `job-migrate` under `verify-full` against Azure** is still the end-to-end proof of ADR 0042; nothing offline can show it.
10. **Alerts stays a loop.** The architect's cheaper design (a one-minute scheduled job) was built, measured and rejected by the numbers above; if Container Apps later offers a concurrency policy, or a dispatch gets faster than about 30 s at 0.25 vCPU, revisit (parked below).
11. **Scale to zero versus the first visitor.** With the api at min 0 the first request after about 5 idle minutes meets a 20-30 s cold start; Microsoft's cold-start page says to retry on the client and gives a 240 s ingress timeout, and whether the ingress holds the request is not documented. Hence the warm policy and the BFF timeout variables (row 23).
12. **`template_checks.py` is large (about 1,400 lines)** because `bicep snapshot` leaves every expression that touches a secure parameter unevaluated, so the checker evaluates the compiled ARM expressions itself. It is test code, mutation-tested through `tests/run.sh`; the maintenance cost is the price of asserting the review-focus invariants offline.
13. **The `Environment Management Hour` meter is an open cost risk** (USD 73 a month if it applies). If Cost Analysis shows it, tell the architect: the alternatives are the Render fallback (about USD 28 a month at the measured sizes, no UAE region) or the single-VM option (parked below).
